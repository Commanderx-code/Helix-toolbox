# Working on Helix Toolbox

Guidance for anyone, person or coding agent, changing this repository.
[CONTRIBUTING.md](CONTRIBUTING.md) is the same for people, with how to get
started and open a pull request.

## What this is

A Rust workspace: `apps/helix-toolbox` (command line and terminal interface),
`crates/helix-toolbox-core` (data model), `crates/helix-toolbox-catalog` (reading
and validating `catalog/` and `scripts/`), `crates/helix-toolbox-platform`
(distribution detection), `crates/helix-toolbox-engine` (plans, runners, the
pseudo-terminal, history). `docs/ARCHITECTURE.md` explains how they fit;
`docs/MIGRATION.md` records how the previous toolbox, Commander Toolbox (now
archived), came across; its repository stays the reference for how an entry
used to behave.

## Rules

- Interfaces never change the system. They ask the engine for a plan and run
  it through a runner. New operations go in the engine, not in the interface.
- The shell program never contains free text: only quoted literals from the
  validated catalog. Keep `helix_toolbox_core::valid_package_name` and
  `valid_id` in front of anything that reaches a command line.
- Tested installers from the previous toolbox are brought across, not
  rewritten, unless there is a reason that is written down.
- Tests must not change the machine they run on. Fixtures live in
  `tests/fixtures/`; real runs in tests write only to temporary directories.
- Commander Toolbox is archived; do not reopen it. Fixes go here.

Catalog files whose first line says they were generated by
`scripts/sync-sources.py` belong to the dotfiles or Myfish repository's
`toolbox.json`; change that, not the rendered file.

## Checks

`scripts/verify.sh` runs everything the workflows run before a build is
published: `cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace`,
the installer tests, shellcheck, a fresh render of the dotfiles and Myfish
exports (which must change nothing), a release build, and the walkthrough
regeneration (`helix-toolbox docgen docs/walkthrough.md`, which must leave no
diff). Run it before committing, and check its exit status rather than the
end of its output. `docs/TESTING.md` explains the test layers.

## Conventions

- Commits are plain messages in the repository owner's name, with no
  attribution lines for tools or assistants.
- Catalog entries are one TOML file per entry; see `docs/CATALOG.md` for
  the format. Scripts referenced by id live in `scripts/installers/`; the
  installers from the previous toolbox are under `scripts/installers/commander/`
  with their tests in `tests/installers/`, and `scripts/verify.sh` runs both.
- Documentation does not say that something was written by an AI tool.
