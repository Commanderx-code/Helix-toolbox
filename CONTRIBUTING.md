# Contributing to Helix Toolbox

Thank you for helping. Bug reports and ideas go in the
[issue forms](https://github.com/Commanderx-code/Helix-toolbox/issues/new/choose);
[docs/REPORTING.md](docs/REPORTING.md) says what makes a report useful.
Security problems go through the private route in
[docs/SECURITY.md](docs/SECURITY.md) instead. This page is for changing the
code, the catalog or the documentation.

## Getting started

You need Rust 1.89 or newer ([rustup](https://rustup.rs)), Python 3, and
shellcheck for the full checks.

```sh
git clone https://github.com/Commanderx-code/Helix-toolbox.git
cd Helix-toolbox
cargo run -p helix-toolbox              # the menu, from source
cargo run -p helix-toolbox -- --help    # the command line
scripts/verify.sh                    # everything CI checks
```

Running entries changes the machine you run them on. While developing, use
`--dry-run`, `plan`, a virtual machine, or the fixture catalog the tests use
(`--catalog-dir tests/fixtures/catalog`).

## How the code is organized

```text
apps/helix-toolbox/            the command line and the terminal interface
crates/helix-toolbox-core/     the data model: tabs, groups, entries, actions, risk
crates/helix-toolbox-catalog/  loading and validating the catalog and scripts
crates/helix-toolbox-platform/ distribution and package manager detection
crates/helix-toolbox-engine/   plans, the shell program, runners, the pseudo-terminal, history
catalog/                    the entries, one TOML file each, in six areas
scripts/shared/             the shell helpers scripts source
scripts/installers/         the scripts by id: commander/ from the previous toolbox, the rest from Linutil's catalog
tests/installers/           the installers' Python tests, run against fixtures
tests/fixtures/             a small catalog for the end-to-end tests
docs/                       architecture, roadmap, security, migration matrix, walkthrough
assets/                     the banner, the logo (transparent) and the app icon
```

[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) explains how the crates fit
together, and [docs/CATALOG.md](docs/CATALOG.md) how an entry is written and
how a run is planned.

History lives in `~/.local/state/helix-toolbox/history.jsonl` with saved output
and the tracing log under `logs/` beside it; `XDG_STATE_HOME` is honored and
`HELIX_TOOLBOX_LOG` sets the log level. A run in progress keeps a marker under
`running/`; if Helix Toolbox is closed or killed before the run is recorded, the
next start lists it as not finished, or with its real result if it had ended.

## Rules

- Interfaces never change the system themselves. They ask the engine for a
  plan and run it through a runner; new operations go in the engine.
- The shell program contains no free text, only quoted literals from the
  validated catalog. Keep `helix_toolbox_core::valid_package_name` and
  `valid_id` in front of anything that reaches a command line.
- Text from outside Helix Toolbox that is shown in the terminal goes through
  `printable()`.
- Installers carried over from the previous toolbox are brought across, not
  rewritten, unless there is a reason that is written down.
- Tests do not change the machine they run on: fixtures live in
  `tests/fixtures/`, and real runs in tests write only to temporary
  directories.
- What [docs/STABILITY.md](docs/STABILITY.md) promises (commands, JSON,
  files, entry ids) does not break within 1.x.

Catalog files whose first line says they were generated by
`scripts/sync-sources.py` belong to the dotfiles or Myfish repository's
`toolbox.json`; change that, not the rendered file.

Helix Toolbox replaces Commander Toolbox, now archived;
[docs/MIGRATION.md](docs/MIGRATION.md) records where each of its entries went.
Entries from the dotfiles and Myfish repositories follow those repositories
automatically; [docs/SOURCE-SYNC.md](docs/SOURCE-SYNC.md) describes how, and
how a release is published from every tested revision.

## Checks

```sh
scripts/verify.sh
```

runs the formatter, clippy, the Rust tests (including the program driven in
a pseudo-terminal against a fixture catalog), the installer tests,
shellcheck, a fresh render of the dotfiles and Myfish exports, a release
build and the walkthrough. The Checks workflow runs the same on every pull
request. [docs/TESTING.md](docs/TESTING.md) describes the test layers and
what they cannot cover.

Run it before you open a pull request, and check its exit status rather than
the end of its output.

## Pull requests

- One change per pull request, with a plain description of what changed and
  why, and how it was tested.
- Commit messages are plain sentences in your own name.
- Pull requests to `main` run the Checks workflow; changes to package
  handling also get the Distributions run in real Arch, Debian, Ubuntu,
  Fedora and openSUSE containers.
- Each merged change becomes a release.

## Releases

Releases are numbered `vMAJOR.MINOR.PATCH`, starting at v0.1.0: each release
adds one to the patch number, and `helix-toolbox --version` reports it. To start
a new series, set the version in `Cargo.toml` (`[workspace.package]`) to, say,
`0.2.0` or `1.0.0`; the next release takes it.
[docs/RELEASING.md](docs/RELEASING.md) walks through a release, including
publishing the crates to crates.io.
